- 七大软件架构设计原则
  - 学习设计原则是学习设计模式的基础。在实际开发过程中，并不是一定要求所有代码都遵循 设计原则，而是要综合考虑人力、时间、成本、质量 不刻意追求完美，要在适当的场景遵循设 计原则 。这体现的是一种平衡取舍，可以帮助我们设计出更加优雅的代码结构
  - 开闭原则
    - 通常程序只支持扩展，不支持修改。这就是开闭原则
      - 开闭原则 对扩展开放，对修改关闭 降低维护带来的新风险
  - 依赖倒置原则
    - A高层次的模块不应该依赖于低层次的模块，他们都应该依赖于抽象。 B.抽象不应该依赖于具体实现，具体实现应该依赖于抽象。（比如接口）
      - 高层不应该依赖低层 更利于代码结构的升级扩展
  - 单一职责原则
    - 职责P1和职责P2。当因为职责P1的需求发生改变而需要修改类T的时候，有可能会导致原本运行正常的职责P2功能发生故障
      - 一个类只干件事 便于理解，提高代码的可读性
  - 接口隔离原则
    - 类间的依赖关系应该建立在最小的接口上
      - 接口的设计粒度越小，系统越灵活，这是不争的事实。但是，灵活的同时也带来了结构的复杂化，开发难度增加，可维护性降低，这不是一个项目或产品所期望看到的，所以接口设计一定要注意适度
        - 一个接口只干一件事 功能解剿，高~合、低鹅合
  - 迪米特法则
    - 尽量降低类与类之间的耦合（例子类里面不要定义类，用传参的方式）
      - 不该知道的不要知道 只和朋友交流，不和陌生人说话，减少代码 脆肿
  - 里氏替换原则
    - 子类可以替换父类，里氏代换原则是对“开-闭”原则的补充
      - 子类重写方法功能发生改变，不应该影响父类方法 的含义 防止继承泛滥
  - 合成复用原则
    - 合成复用原则就是在一个新的对象里通过关联关系（包括组合关系和聚合关系）来使用一些已有的对象，使之成为新对象的一部分；新对象通过委派调用已有对象的方法达到复用功能的目的。简言之：复用时要尽量使用组合/聚合关系（关联关系），少用继承
      - 尽量使用组合实现代码复用，而不使用继承 降低代码销合

- 创建型设计模式
  - 工厂模式
    - 在日 常开发中，凡是需要生成复杂对象的地方，都可以尝试考虑使用工广模式来代替。
    - 简单工厂模式（test01）
      - 简单工厂模式的工厂类 ，负责所有产品的创建，但当产品基数增多时，工厂 代码会非 常腕肿 ，违背高聚合原则
    - 工厂方法模式(test02)
      - 典型的解藕框架。高层模块只需要知道产品的抽象类，无须关心其他实现类，满足迪米 特法则、依赖倒置原则和里氏替换原则。3)抽象产品只能生产一种产品，此弊端可使用抽象工厂模式解决。
    - 抽象工厂模式（test03）
      - 规定了所有可能被创建的产品集合，产品族中扩展新的产品困难，需要修改抽象工厂 的接口. 增加了系统的难理解性
      - spring中用到了
  - 单例模式(test04)
    - 单例模式可以保证内存里只有一个实例，减少了内存的开销.
    - spring中用到节省内存
  - 原型模式(test05)
    - 重写clone()方法，只会深克隆类和类中所有非基本数据类型的属性对应的类。对于类中的属性对应的类，是无法深克隆的，如果深克隆类中的属性对应的类，需要额外的调用类中的属性对应的类clone方法
  - 建造者模式(test06)
    - 如果将抽象工厂模式看成汽车配件生产工厂，生产一个产品族的产品，那么建造者模式就是一个汽车组装工厂，通过对部件的组装可以返回一辆完整的汽车
    - date jpa sql 拼接 jdk源码StringBuilder的append方法
    - 使用环境（1）需要生成的产品对象的属性相互依赖，需要指定其生成顺序 （2）需要生成的产品对象有复杂的内部结构，这些产品通常包含多个成员变量 （3）对象的创建过程独立于创建该对象的类。在建造者模式中通过引入指挥者类，将创建过程封装在指挥者类中，而不在建造这类和客户类中 （4）隔离复杂对象的创建和使用，并使得相同的创建过程创建不同的产品

  - 代理模式(test07)
    - 代理模式又叫委托模式，是为某个对象提供一个代理对象，并且由代理对象控制对原对象的访问。代理模式通俗来讲就是我们生活中常见的中介
  - 门面模式(外观模式)（test08）
    - 门面模式又叫做外观模式，提供了一个统一的接口，用来访问子系统一群接口，比如jar和第三方sdk
    - SpringJDBC下的jdbcUtils和MyBatis源码的Configuration 有很多new开头的 tomcat源码 requesFacade类为例

    - 装饰器模式提供了比继承更有弹性的替代方案(扩展原有对象的功 〉将功能附加到对象上. 因此 装饰器模式的核心是功能扩展 使用装饰器模式可以透明且动态地扩展类的功能. )动态地给 个对象添加功能，这些功能可以再动态地被撤销.

    - 解决java中有某个对象大量创建从而降低内存消耗本质就是缓存多处使用,享元模式其实是工广方法模式的一个改进机制
  - 组合模式(整体部分模式)(test11)
    - 可以清楚地定义分层次的复杂对象，表示对象的全部或部分层次，使得增加新构件也更容易。 客户端调用简单，客户端可以一致的使用组合结构或其中单个对象。 定义了包含叶子对象和容器对象的类层次结构，叶子对象可以被组合成更复杂的容器对象，而这个容器对象又可以被组合，这样不断递归下去，可以形成复杂的树形结构。 更容易在组合体内加入对象构件，客户端不必因为加入了新的对象构件而更改原有代码
